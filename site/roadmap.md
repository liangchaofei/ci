# 课程路线与最终验收

这是一门**只实现 Agent Runtime** 的课程。最终作品不是 Coding Agent、不是可复用 Agent SDK，也不是多 Agent 平台。它要能够可靠地驱动一种任务：准备模型输入、接收模型决策、受控执行工具、记录观察、继续或结束。我们用修复代码的场景解释为什么需要这些机制，但文件编辑和测试工具在这里首先是**受控执行的演示能力**，不是完整 Coding Agent 产品。

## 先约定“完整”的边界

完成本课程后，应得到一个可本地运行的 Runtime，支持真实模型与可预测的模型替身、工具调用与结果回写、流式事件、预算与取消、任务状态、会话持久化、恢复、审批和基础隔离，并有覆盖正常与失败路径的场景测试。它是**功能完整、可教学验证的单机实现**。容器集群、跨机器调度、密钥托管服务和生产容量验证需要独立的平台工程，不能由本地测试声称完成。

Pi 的 [Agent Core](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/agent/README.md)提供一个重要参照：有状态 Agent、工具执行、事件流、低层循环和消息转换各有边界。课程对照固定在提交 `8efd314`；Pi 的后续改动不会悄悄改变本课程解释。课程先实现自己的需求并观察轨迹，然后只读 Pi 对应的局部源码。

当前招聘信息也提示了工程边界：[OpenAI 的 Agent Systems 岗位](https://openai.com/careers/ai-systems-engineer-codex-agents-san-francisco/)提到执行循环、沙盒、编排、评估和可靠性；[Anthropic 的 Agent Runtime Platform 岗位](https://job-boards.greenhouse.io/anthropic/jobs/5316593008-41)强调受控环境、隔离和凭据管理。它们用于检查知识覆盖，不能把一个教学仓库等同于这些团队运行的平台。

## 贯穿全书的一条场景

示例任务是：“一个 `sum(numbers)` 函数在空数组时失败，请找出原因，并在允许的工作区里验证修复。”

第 01 篇只模拟**读取源码并给出有依据的诊断**；后续逐步接入模型适配、工具注册、受控工作区、修改提议、测试和完成证据。Runtime 永远不内置 `sum` 的业务规则。换成另一个任务时，循环、事件和会话机制不应重写。

正向轨迹：读到源码 → 观察进入会话 → 模型提出下一步 → 受控执行 → 同一任务状态更新 → 检查证据 → 结束。

反向轨迹：读取路径越界、模型只输出“已修好”、工具超时后是否产生副作用未知、恢复时工作区版本变化。这些情况不能靠一句提示词纠正，而要改变 Runtime 的控制流。

## 章节依赖

章节编号是学习顺序，不强迫每篇同样长。每篇必须能独立完成一项有意义的行为与故障验证；不能把一个未完成的实现拆成几页只有概念的“章节”。

| 章节 | 解决的工程问题 | 本章新增的可运行证据 |
|---|---|---|
| 00 项目起点与架构 | 什么属于 Runtime，怎样验证环境可靠 | Node/TypeScript、测试、网页构建通过；能区分类型和行为失败 |
| 01 第一条反馈闭环 | 执行结果怎样进入下一次决策 | 从请求、执行、手动反馈逐步走到通用循环；下一次决策看到执行器返回结果 |
| 02 消息、State 与 Context | 程序事实和模型输入为何不同 | 从最新状态构造本轮消息输入；不整体传出 State 的顶层控制字段 |
| 03 工具契约与执行入口 | 模型的工具请求为何不能直接执行 | 注册、参数校验、调用 ID 关联、结构化错误及前置拒绝 |
| 04 停止、取消与时间边界 | 挂起请求怎样停止等待，迟到结果如何处理 | 预算、超时、外部取消走不同出口；迟到工具结果不写回 |
| 05 真实模型适配 | 怎样把内部消息与模型协议接起来 | 一种真实模型适配器能完成非流式多轮工具调用；替身仍可复现 |
| 06 流式响应 | 增量文本和不完整工具参数何时可以提交 | 事件可见，完整响应才进入会话并触发工具；断流不执行半个调用 |
| 07 工具批次与并发 | 一个模型响应包含多个调用时怎样保持关联 | 顺序与并行执行可切换；完成顺序变化不篡改调用关系 |
| 08 上下文窗口与预算 | 长会话怎样控制模型输入与成本 | 选择、裁剪与摘要保留关键约束和证据；轮数、时间和用量分开记 |
| 09 事件、Trace 与运行实例 | 怎样观察运行并防止同一实例重入 | 有状态 Agent、事件订阅、稳定事件顺序与可复查轨迹 |
| 10 新输入与暂停 | 运行中用户追加信息或等待人工时怎样继续 | steer/follow-up 队列有明确消费顺序；暂停不会伪装成完成 |
| 11 会话日志与检查点 | 进程退出后凭什么恢复正确状态 | 追加式记录、快照和版本；重启后可重建模型输入与任务状态 |
| 12 恢复与未知副作用 | 超时或崩溃后为什么不能盲目重放写操作 | 已确认与未知结果区分；恢复前核对资源版本与权限 |
| 13 权限、审批与执行隔离 | 模型请求怎样获得有限的执行权 | 策略在执行前拦截；拒绝和审批过期均不能触发副作用 |
| 14 错误分类与重试 | 哪些失败可重试，怎样防止重试放大伤害 | 传输错误、模型错误、工具错误和任务失败分开；只对安全操作重试 |
| 15 运行资源控制 | 怎样限制 token、费用、并发和持续时间 | 运行用量可追踪；预算耗尽和用户取消有不同事件与结果 |
| 16 场景评估与故障注入 | 怎样用完整场景检查 Runtime 可靠性 | 多轮、断流、越权、崩溃恢复、乱序完成的端到端回归 |
| 17 系统整合与源码复盘 | 各模块是否真的组成同一个 Runtime | 一条完整正常轨迹和多条失败轨迹贯穿模型、工具、状态、事件、恢复与门禁 |

第 01–04 篇得到**确定性的核心循环**；第 05–09 篇得到可交互、可观察的单次运行；第 10–15 篇补齐长期运行和执行控制；第 16–17 篇用完整场景收口。显式 Planning、Graph、RAG、MCP 和多 Agent 不作为 Runtime 必备章节。它们以后可以作为应用或扩展专题，不能替代基础运行语义。

## 最终验收矩阵

第 17 篇结束时，要在同一个仓库、同一个 Runtime 入口下验证：

| 情况 | 必须观察到的事实 |
|---|---|
| 正常多轮 | 第 `n+1` 次模型请求包含第 `n` 次已确认的工具结果 |
| 无证据完成 | 模型声称成功但验证事实不足，结果不能标成完成 |
| 参数错误与拒绝 | 执行器未被调用，拒绝原因进入记录与模型可见结果 |
| 流式中断 | 未完成的工具调用不执行；事件和最终状态说明中断位置 |
| 并发结果乱序 | 每个结果仍关联原调用 ID，记录顺序有定义 |
| 取消与超时 | 停止等待，迟到结果不能改变最终状态；外部副作用未知时明确报告 |
| 暂停审批 | 未获批准的写入无法执行；恢复要重新确认有效权限 |
| 崩溃恢复 | 会话重建后不丢已确认事实，也不自动重放未知写操作 |
| Context 预算 | 关键目标、权限和验证证据保留，模型输入有可追踪来源 |
| 可观测性 | 从同一 Trace 找到每轮模型请求、工具调用、结果、用量和退出原因 |
| 任务隔离 | 两个运行实例不共享可变状态、调用 ID 或审批结果 |

## 每篇正式教程的发布标准

教程正文按“问题与系统位置 → 具体数据轨迹 → 新增/修改文件 → 分步代码与紧邻讲解 → 集成运行 → 调试与故障实验 → Pi 局部对照 → 完整文件汇总”组织。**代码块必须能合起来运行**；每步明确创建、追加或替换的位置，示意片段明确标出不是最终实现。不能用整份代码后接几段概括代替分步教学。

当前先通过类型检查、入口运行、轨迹和故障实验验证，不安排单测编写。第 00 篇已有的环境检查保留；后续若需要系统的自动化回归，再说明引入方式。新增章节先在临时工程复现代码、运行检查和失败路径，再发布到侧边栏。路线图中的未来章节不是教程。

模块较多时，安排较早可运行的阶段，让读者逐步观察新增行为。各阶段复用已有实现并收敛到最终版本；先理解主线，再补可靠性约束。检查每个阶段的迁移、命令和输出，不只验证最后一次运行。模拟能力标明未来替换位置，并用一个小迁移需求检查职责边界。

课程网页源码位于 `site/`。本地运行 `npm run site:dev`；静态构建运行 `npm run site:build`。GitHub Pages 部署会在课程内容确认后单独配置与发布。
