第 02 篇：程序保存什么，决策方看到什么 ​

第 1 篇已经能完成一次模拟诊断：提出读取请求，执行读取，保存源码，再提出答案。本篇继续使用这些代码，不重写循环，也不接入真实模型。

读完这篇，你会得到什么 ​

  • 要解决的问题： 程序保存了工具结果，为什么本轮决策仍可能收到旧信息？怎样避免把运行管理字段也整份传过去？
  • 要理解的知识： 程序持有的运行状态（State）与本轮决策输入（Context）有什么区别；复制数据、选择字段和准备最新输入分别解决什么问题。
  • 要动手完成的内容： 新建 context.ts 准备消息输入，先观察读取前后的两份 Context，再将它接回原有循环。
  • 在整个 Runtime 中的位置： 本篇补上“状态更新之后、请求决策之前”的输入准备步骤，为后续真实模型适配建立边界。

完成后，应能分别定位“结果没保存”和“结果保存了但没有用于本轮输入”这两类错误。本篇仍使用第 1 篇的模拟诊断，不接入真实模型，也暂不做消息裁剪与摘要。

需要回看第 1 篇时，先找工具结果追加到 state.messages 和下一次调用 decide 的两处位置；本篇的新模块连接这两处。正文会解释所需知识，外部链接供查证。

先把 Runtime 放回整条运行链 ​

用户提出“找出空数组求和为什么失败”，模型不会因为应用收到了这句话，就自动读到磁盘、记住工具结果、维护次数限制。需要程序把这些步骤接起来。本系列把组织这段运行过程的程序称为 Runtime。

先看当前几个模块怎样协作。绿色框是 Runtime 持有的职责，右侧函数由场景提供，底部灰色条列的是后续能力：

模型负责依据收到的信息提出下一步；工具负责实际读取、查询等操作；Runtime 负责把它们按明确规则组织起来。第 1 篇的脚本暂时代替模型，读取函数也返回固定源码，但调用、记录与退出已经由真实代码完成。

完整 Runtime 的其他部分以后会接入这条链：

部分负责的问题当前进度
循环与运行状态谁安排下一步，执行结果保存在哪里，何时结束第 1 篇已实现最小版本
输入准备从当前状态取哪些信息交给本轮决策本篇实现
模型适配怎样把内部数据变成模型接口请求后续接入真实模型
工具执行入口怎样找到工具、检查参数并关联结果目前是一个模拟读取函数，后续扩展
运行控制等待太久或用户取消时怎样退出后续实现
事件与会话存储怎样观察过程，进程结束后怎样恢复后续实现

这些部分不是几套独立 Agent。它们围绕同一次任务协作，后续章节会逐步接入。现在不用背完整架构，先抓住这一条关系：Runtime 保存最新记录，再用这些记录准备下一轮输入。

为什么不继续把 State 整个传过去 ​

第 1 篇调用 decide 时传入状态副本。这样可以演示反馈，但这个参数同时包含了两类信息：

State 中的信息谁需要它本篇怎样处理
用户目标决策方需要知道要解决什么保留在第一条 user 消息中
之前提出的动作决策方需要知道已经请求过什么保留在 assistant 消息中
工具结果决策方需要知道实际取得什么保留在 tool 消息中
decisionsRuntime 用它检查还能否继续决策不放进本轮输入的顶层字段

如果决策器直接读取 decisions，它就和循环内部计数耦合了。以后循环新增运行编号、等待状态或其他管理字段，也容易被整份带过去。为避免这种依赖，本篇建立一个独立的输入类型，并明确选择交出的字段。

在本项目中，State（运行状态）是 Runtime 持有的本次运行信息；Context（上下文）是为本轮决策准备的信息。后者不是另一份永久状态，也不会自动跟随 State 更新。

Anthropic 对上下文的讨论关注模型本次生成时可用的信息，并强调在多轮过程中持续准备这些信息。本篇先实现其中很小的一步：明确构造消息输入；还不做长会话裁剪、摘要或用量计算。来源：Anthropic《Effective context engineering for AI agents》

这里的 DecisionContext 是本教程内部类型，当前只含消息。它还不是某家模型 API 的请求对象，消息中的 Action、ToolResult 也暂时保留内部形状。真实模型接入时，再增加相应协议转换。

同一个概念在代码里有几种名字 ​

哪些数据保存，哪些只供这次调用使用 ​

数据谁创建或取得谁保存、怎样继续使用
state集成运行时由 runAgentLoop 初始化；观察入口中手动初始化循环更新它，结束时通过 RunResult 交回入口
contextbuildDecisionContext 从当前 state 生成本轮交给 decide；下一轮从最新 state 重新构造，不写入 State
actiondecide 返回循环先取得它，再包装为 assistant 消息追加到 state.messages
工具 resultexecuteTool 返回循环确认调用身份后，包装为 tool 消息追加到 state.messages

这里的“保存”先指保存在运行中的 JavaScript 对象里，不是已经落盘。会话文件和进程重启后的恢复还没有实现。

因此，本篇不是 State → Context → 再把 Context 塞回 State。它走的是：从 State 准备输入 → decide 返回动作 → 记录动作 → 必要时执行工具并记录结果 → 再从新 State 准备输入。

context.ts 不发请求、不执行工具、不更新运行状态，只准备输入。输入规则有自己的变化原因，因此单独成模块；循环调用它即可，不需要逐渐把所有处理都写进 agent-loop.ts。

本篇分两阶段。先单独观察 Context，得到一个可运行结果；再修改决策接口，把它接回原有循环。暂不新增单测或依赖。

阶段 1：先看到两份不同的 Context ​

1.1 定义本轮决策输入 ​

在 src/runtime/types.ts 的 State 类型之后、Outcome 类型之前，追加：

ts
/** 本轮决策可见的输入；控制字段仍由 Runtime 持有。 */
export type DecisionContext = {
  readonly messages: readonly Message[];
};

它只有 messages。目标并没有丢失，因为第 1 篇已经把目标放进首条 user 消息；此前的请求与源码也分别在 assistant、tool 消息里。

本篇复用已有 Message 类型，是因为消息内容暂时没有转换，只需要把 State 的控制字段与输入分开。以后要改变消息格式时，再在明确的边界转换，不必现在复制一套内容相同的消息类型。

两处 readonly 分别约束 messages 属性重新赋值和数组的直接增删，帮助类型检查发现误操作；嵌套消息对象并不会因此深度冻结。数据独立性要由下一步复制保证。来源：TypeScript 的 readonly 属性与数组

此时先保留原有 Dependencies，尚不修改 decide。这样新增输入模块时，原来的入口仍然能检查和运行。

1.2 新建输入准备模块 ​

创建 src/runtime/context.ts，写入下面的完整模块：

ts
import type { DecisionContext, State } from "./types.ts";

/** 每次决策前，从最新状态准备一份独立的输入。 */
export function buildDecisionContext(state: Readonly<State>): DecisionContext {
  // 明确选择消息；不把 goal、decisions 等顶层控制字段一并交出。
  return { messages: structuredClone(state.messages) };
}

调用方传入最新 state，函数只取 state.messages，复制后装进新的对象。返回对象的顶层只有 messages，decisions 仍留在 Runtime；goal 字段不再重复交出，但目标文字仍在用户消息里。

这里有两个不同动作：明确写出 messages，是选择交出哪些字段；structuredClone 则使消息副本不与 State 共享嵌套对象。只复制整份 State 不能减少字段，只挑出原消息引用又不能保护留存数据。

本章消息包含字符串、数组和普通对象，可以这样复制。Node.js 的 structuredClone 文档说明了这个 API。若以后状态中出现函数或资源句柄，不能假定整份数据都能复制。

这个 return 只是把新对象交回调用处。调用处要用变量接住它，再作为参数传给 decide；这里没有给 state 增加 context 字段，也没有改写 state.messages。工具结果仍须由循环先写回，之后调用本函数，才能进入下一份输入。

阶段 2：把输入准备接回原来的循环 ​

接下来是一次接口迁移：Dependencies、脚本决策器和循环调用处要一起更新。完成这三处前，类型检查可能指出参数不匹配；先按顺序修改，最后统一检查。执行器、完成规则和工具结果写回逻辑都保留。

2.1 改变 decide 的输入约定 ​

在 src/runtime/types.ts 中，将原有 Dependencies 类型整段替换为：

ts
/** 由调用方提供模型、工具和任务完成规则，循环只负责调度。 */
export type Dependencies = {
  // 只接收本轮准备好的消息，不接收 Runtime 的控制字段。
  decide: (context: DecisionContext) => Promise<Action>;
  // 取得一次请求的实际结果，必须回传同一个调用 ID。
  executeTool: (call: ToolCall) => Promise<ToolResult>;
  // 核对当前场景的完成证据，不把模型的 finish 直接当成成功。
  validateFinish: (state: Readonly<State>, answer: string) => boolean;
};

export async function scriptedDecide(context: DecisionContext): Promise<Action> {
  const roles = context.messages.map((message) => message.role).join(" -> ");
  console.log(`[决策 decide] 消息角色（roles）=${roles}`);

    // 复用阶段一的请求创建函数，实际执行仍由调用方安排。

  }

  if (
    lastMessage?.role === "tool" &&
    lastMessage.result.callId === sourceCallId &&
    lastMessage.result.status === "ok" &&
    lastMessage.result.value === sourceCode
  ) {
    return { kind: "finish", answer: diagnosis };

  return { kind: "fail", reason: "No usable source observation" };
}

第一次 context.messages 仍只有 user，因此请求读取；第二次含成功的源码结果，因此提出 finish。分支依据与第 1 篇相同，变化的是信息入口：不再从整份 State 取消息，而从本轮 Context 取消息。

日志去掉了原先通过 state.decisions 计算的序号。脚本不该为了打印序号继续索要 Runtime 控制字段；当前通过消息角色观察输入即可，最终次数仍由集成入口从返回状态中打印。以后统一事件与轨迹会提供更合适的运行标识。

这次改动没有让脚本变聪明，固定源码比较和预设答案仍然存在。我们检查的是输入边界和反馈是否保持正确。

2.3 在每次调用前构造输入 ​

在 src/runtime/agent-loop.ts 顶部现有导入之前新增：

ts
import { buildDecisionContext } from "./context.ts";

循环从独立模块导入准备函数，不在文件里再写一遍消息选择逻辑。

在 runAgentLoop 的 while 内，找到从 let action: Action 开始、到记录 assistant 消息之前的决策 try/catch，将这一段替换为：

ts
let action: Action;
try {
  // 每轮都重新构造，才能包含上一轮刚写回的工具结果。
  const context = buildDecisionContext(state);
  action = structuredClone(await dependencies.decide(context));
} catch (error) {
  return { state, outcome: failure(errorMessage(error), "decision") };
}

先看本例的正常路径。第一次循环用初始 State 构造 Context，交给脚本，拿到读取请求。工具执行、写回后，循环再次来到这里，用更新后的 state 重新构造，于是第二次输入含有源码。

这里的数据流对应两条具体语句：const context = buildDecisionContext(state) 只给局部变量赋值；dependencies.decide(context) 只把这个对象作为函数参数传入。它们都没有写 state。

真正更新状态的地方仍在下方：决策返回后追加 assistant 消息，工具返回后追加 tool 消息。Context 不需要再存进 State，因为它能从已有消息重新生成；本篇没有新增 state.context。

关键是构造位置在 while 内、decide 之前。若只在进入循环前准备一次，State 虽然更新，后面的决策仍只拿到旧输入。第 1 篇解决“结果有没有保存”，本篇进一步保证“保存后的结果有没有用于本次输入”。

buildDecisionContext 已经复制消息，所以这里不再把整份 snapshot(state) 传给 decide。返回动作仍复制后再留存，防止外部函数后续修改同一对象。完成规则处的 snapshot(state) 保留，那是另一条状态访问路径。

本项目暂将输入准备、决策调用和返回动作复制都归在 decision 阶段。任一操作在这个 try 中抛错，会返回该阶段失败；不要因此认定错误一定来自模型服务。

两个故障实验 ​

每次只改一处，观察后恢复。实验都针对本章边界，不新增单测。

实验一：类型变窄，是否就自动少传字段 ​

在 src/runtime/context.ts 中，把唯一的 return 临时替换为：

ts
return structuredClone(state);

运行：

bash

本篇这份代码的类型检查仍会通过，但两处字段日志变为：

text
上下文字段（keys）: goal, messages, decisions

为什么返回类型写了 DecisionContext，实际还有其他字段？TypeScript 允许拥有所需结构的对象被用于这个位置；类型检查不会在运行时删除额外属性。整份 State 本来就有 messages，因此能满足这里的结构要求。来源：TypeScript 的结构类型兼容规则

要控制实际交出的顶层字段，必须构造只含 messages 的新对象。这不是靠换个类型名完成的。

恢复：

ts
return { messages: structuredClone(state.messages) };

重新运行观察入口，确认 keys 回到 messages。本例只选择顶层字段，没有清洗消息内容；若消息里已经写入敏感文字或不应提供的信息，它们仍会被带入，不能将此函数当成完整安全过滤器。

实验二：State 更新了，为什么决策还在重复读取 ​

在 src/runtime/agent-loop.ts 中，紧接 state 初始化之后、while 之前，临时增加：

ts
const cachedContext = buildDecisionContext(state);

再把 while 内原来的 const context = buildDecisionContext(state); 替换为：

ts
const context = cachedContext;

运行集成入口，会看到脚本连续三次只收到 user，并重复请求读取。末尾结果为：

text
运行结果（outcome）: budget-exhausted
决策次数（decisions）: 3
消息顺序（messages）: user -> assistant -> tool -> assistant -> tool -> assistant -> tool

循环确实保存了每次执行结果，所以最终 State 有七条消息；但 cachedContext 始终来自初始 State，决策方一直没有得到后来的源码。增加次数只会重复这个错误，不会让旧副本自行更新。

先删除 while 前新增的 cachedContext，再把循环内恢复为每轮调用 buildDecisionContext(state)。重新检查并运行，应该回到两次决策后 completed。本章仍是固定调用身份的模拟场景；故障中重复读取不是多调用身份生成方案。

换一个目标，检查职责是否分清 ​

在 src/examples/inspect-context.ts 中，临时把 goal 改成“解释为什么空数组求和会抛错”。在第一次 showContext 之前加一行日志：

对照 Pi：调用模型前准备输入 ​

固定提交 8efd314 的 Pi Agent Core 在 streamAssistantResponse 中先取得当前消息，可选地运行 transformContext，再用 convertToLlm 转为模型可理解的消息，之后才发起模型调用。来源：Pi 的输入准备位置

只看这两个问题：输入转换在每次请求前的什么位置？它读的是当前消息还是初始化时的一份旧消息？再对照本篇 while 内 buildDecisionContext 的位置。

Pi 的类型说明还要求将内部消息转换为模型兼容格式，不可转换的界面通知等消息应被过滤。本章尚未加入这些内部消息，也没有实现模型协议转换，只建立“从当前状态准备本轮输入”的边界。来源：Pi 的 convertToLlm 与 transformContext 约定

不要把名称一一套用：Pi 的 AgentContext 还参与它自己的运行组织，并不等于本篇仅含消息的 DecisionContext。我们比较的是调用位置和责任划分，类型名称与最小字段由本项目选择。

本篇完成后，系统多了什么 ​

沿本章的数据表与两个快照，可以找到每次输入的来源和消息写回的位置。Context 是可重新构造的输入；State 是继续推进任务所需的运行记录，两者在本实现中没有相互嵌套。

现在分别能定位两类问题：State 里根本没有工具结果，调查执行后的写回；State 已有结果但 Context 没有，调查输入构造的位置和字段选择。后续工具注册、模型适配、事件与存储都会沿各自职责加入这条运行链，不需要每次从零重写循环。

本篇没有新增模型能力，也没有完成摘要、裁剪或权限隔离。下一篇会处理另一条边界：决策方提出工具请求后，程序怎样找到对应工具、检查输入，再进入执行。

/** 模型提出的工具请求；id 标识一次调用，name 标识工具种类。 */
export type ToolCall = {
  id: string;
  name: string;
  arguments: Record<string, unknown>;
};

/** 工具执行后得到的事实；失败不能伪装成成功值。 */
export type ToolResult =
  | { callId: string; status: "ok"; value: unknown }
  | { callId: string; status: "error"; message: string };

/** 模型提出的请求。finish 仍要经过应用的完成验证。 */
export type Action =
  | { kind: "tool"; call: ToolCall }
  | { kind: "finish"; answer: string }
  | { kind: "fail"; reason: string };

/** 本章的最小会话记录，按发生顺序追加。 */
export type Message =
  | { role: "user"; content: string }
  | { role: "assistant"; action: Action }
  | { role: "tool"; result: ToolResult };

/** 一次运行的当前事实；不同运行不能共享这个对象。 */
export type State = {
  goal: string;
  messages: Message[];
  decisions: number;
};

/** 本轮决策可见的输入；控制字段仍由 Runtime 持有。 */
export type DecisionContext = {
  readonly messages: readonly Message[];
};

/** Runtime 的退出原因，与会话里保留的事实分别表达。 */
export type Outcome =
  | { status: "completed"; answer: string }
  | {
      status: "failed";
      reason: string;
      source: "decision" | "execution" | "validation";
    }
  | { status: "budget-exhausted" };

export type RunResult = { state: State; outcome: Outcome };

/** 由调用方提供模型、工具和任务完成规则，循环只负责调度。 */
export type Dependencies = {
  // 只接收本轮准备好的消息，不接收 Runtime 的控制字段。
  decide: (context: DecisionContext) => Promise<Action>;
  // 取得一次请求的实际结果，必须回传同一个调用 ID。
  executeTool: (call: ToolCall) => Promise<ToolResult>;
  // 核对当前场景的完成证据，不把模型的 finish 直接当成成功。
  validateFinish: (state: Readonly<State>, answer: string) => boolean;
};

ts
import { buildDecisionContext } from "./context.ts";
import type {
  Action,
  Dependencies,
  Outcome,
  RunResult,
  State,
  ToolResult,
} from "./types.ts";

/** 保护循环拥有的消息；当前 State 只包含可结构化复制的数据。 */
function snapshot(state: State): Readonly<State> {
  // 依赖只能改自己的副本；不能修改 Runtime 留存的消息。
  return structuredClone(state);
}

function failure(reason: string, source: "decision" | "execution" | "validation"): Outcome {
  return { status: "failed", reason, source };
}

function errorMessage(error: unknown): string {
  return error instanceof Error ? error.message : String(error);
}

/**
 * 驱动一次任务，并返回最后状态与退出原因。
 * maxDecisions 限制取得 Action 的次数；一次决策最多请求一个工具。
 */
export async function runAgentLoop(
  goal: string,
  dependencies: Dependencies,
  maxDecisions: number,
): Promise<RunResult> {
  if (!Number.isInteger(maxDecisions) || maxDecisions < 1) {
    throw new RangeError("maxDecisions must be a positive integer");
  }

  // State 只属于这次调用；再次运行会得到新的消息与计数。
  let state: State = {
    goal,
    messages: [{ role: "user", content: goal }],
    decisions: 0,
  };

  while (state.decisions < maxDecisions) {
    let action: Action;
    try {
      // 每轮都重新构造，才能包含上一轮刚写回的工具结果。
      const context = buildDecisionContext(state);
      action = structuredClone(await dependencies.decide(context));
    } catch (error) {
      return { state, outcome: failure(errorMessage(error), "decision") };
    }

    // 先记下模型提出了什么，再判断能否执行或完成。
    state = {
      ...state,
      decisions: state.decisions + 1,
      messages: [...state.messages, { role: "assistant", action }],
    };

    if (action.kind === "fail") {
      return { state, outcome: failure(action.reason, "decision") };
    }

    if (action.kind === "finish") {
      try {
        // 模型的完成请求不是成功事实，必须交给应用规则核对。
        if (dependencies.validateFinish(snapshot(state), action.answer)) {
          return { state, outcome: { status: "completed", answer: action.answer } };
        }
        return { state, outcome: failure("Completion lacks verified evidence", "validation") };
      } catch (error) {
        return { state, outcome: failure(errorMessage(error), "validation") };
      }
    }

    let result: ToolResult;
    try {
      result = structuredClone(await dependencies.executeTool(structuredClone(action.call)));
    } catch (error) {
      // 执行错误也是观察，下一轮决策需要知道这次调用失败了。
      result = { callId: action.call.id, status: "error", message: errorMessage(error) };
    }

    // 一个调用的结果不能写到另一个调用名下。
    if (result.callId !== action.call.id) {
      return {
        state,
        outcome: failure("Tool result callId does not match the request", "execution"),
      };
    }

    // 只有确认属于本次调用的结果才能进入 State，供下一轮 decide 使用。
    state = { ...state, messages: [...state.messages, { role: "tool", result }] };
  }

  return { state, outcome: { status: "budget-exhausted" } };
}

import type { Action, DecisionContext, State, ToolCall, ToolResult } from "../runtime/types.ts";

const sourcePath = "src/sum.ts";
const sourceCallId = "read-1";

/** 只创建读取请求；返回这个对象不会执行读取。 */
export function createReadSourceCall(): ToolCall {
  return {
    id: sourceCallId,
    name: "read_source",
    arguments: { path: sourcePath },
  };
}

// 固定字符串代替磁盘内容，先把运行过程变成可重复观察的过程。
const sourceCode =
  "export const sum = (numbers: number[]) => numbers.reduce((a, b) => a + b);";

/** 模拟单个读取工具；只接受本例支持的名称和路径。 */
export async function simulateReadSource(call: ToolCall): Promise<ToolResult> {
  console.log(`[执行工具 execute] ${call.name} 文件路径（path）=${String(call.arguments.path)}`);

  if (call.name !== "read_source") {
    return { callId: call.id, status: "error", message: "Unsupported tool" };
  }

  if (call.arguments.path !== sourcePath) {
    return { callId: call.id, status: "error", message: "Source path is not allowed" };
  }

  return { callId: call.id, status: "ok", value: sourceCode };
}

const diagnosis = "sum([]) fails because reduce has no initial value";

/** 按状态返回预设动作，扮演模型；不能分析任意源码。 */
export async function scriptedDecide(context: DecisionContext): Promise<Action> {
  const roles = context.messages.map((message) => message.role).join(" -> ");
  console.log(`[决策 decide] 消息角色（roles）=${roles}`);

  const lastMessage = context.messages.at(-1);
  if (lastMessage?.role === "user") {
    // 复用阶段一的请求创建函数，实际执行仍由调用方安排。
    return { kind: "tool", call: createReadSourceCall() };
  }

  if (
    lastMessage?.role === "tool" &&
    lastMessage.result.callId === sourceCallId &&
    lastMessage.result.status === "ok" &&
    lastMessage.result.value === sourceCode
  ) {
    return { kind: "finish", answer: diagnosis };
  }

  return { kind: "fail", reason: "No usable source observation" };
}

/** 核对固定诊断与固定读取证据，不证明任意代码诊断正确。 */
export function hasDiagnosisEvidence(state: Readonly<State>, answer: string): boolean {
  if (answer !== diagnosis) return false;

  return state.messages.some((message) => {
    if (message.role !== "tool") return false;

    return (
      message.result.callId === sourceCallId &&
      message.result.status === "ok" &&
      message.result.value === sourceCode
    );
  });
}

let state: State = {
  goal,
  messages: [{ role: "user", content: goal }],
  decisions: 0,
};

const firstContext = buildDecisionContext(state);
showContext("读取前", firstContext);

// 手动补入一次请求与结果，单独观察 State 到 Context 的变化。

const result = await simulateReadSource(call);

  ...state,
  decisions: state.decisions + 1,
  messages: [
    ...state.messages,
    { role: "assistant", action: { kind: "tool", call } },
    { role: "tool", result },
  ],
};

const secondContext = buildDecisionContext(state);
showContext("读取并写回后", secondContext);
console.log(`旧上下文消息数（oldMessages）: ${firstContext.messages.length}`);
console.log(`状态中的决策次数（decisions）: ${state.decisions}`);
