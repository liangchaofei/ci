# CI Agent Harness：项目交接与教学约定

> 更新日期：2026-10-13。本文是换到新对话时的项目入口，也是接下来动手前的共同约定。先读“当前真实进度”，不要把路线图当作已完成事项。

## 1. 为什么要做这个项目

学习者已经听过 AI Agent 理论主线，但明确反馈：能判断一些局部问题，仍不能稳定地把 Agent 的各层串成系统，也没有亲手设计和实现的证据。单纯继续讲章节或连续提问，不会自动解决这个问题。

本项目用一个逐步长出来的 Coding Agent 作为贯穿场景，让学习者亲手建立以下因果链：

```text
目标与成功标准
-> 当前任务 State 与可用 Context
-> 决策/计划
-> 受控工具调用
-> Observation
-> State Update
-> 验证、继续、重规划、暂停或结束
```

然后把 Memory、RAG、MCP、Graph、多 Agent、Evaluation 和企业治理放到确实需要它们的工程场景中。项目最终应让学习者不仅知道模块名字，还能解释运行轨迹、预测异常路由、修改代码并设计能抓住错误的测试。

### 成功标准

1. 有一套可运行、可测试的自研 Agent Runtime 核心和基于它的 Coding Agent 示例。
2. 每个关键模块的任务、输入、输出、状态变化、失败边界和测试都能被学习者独立解释。
3. 至少有一条完整正常轨迹，以及工具失败、权限拒绝、工作区冲突、验证不通过或预算耗尽等异常轨迹。
4. 企业级设计要求被具体门禁和测试表达，不只写在架构图或提示词里。
5. `docs/` 的公开教程能让没有看过原对话的初学者从头跟做，并与对应课程版本的可运行代码一致。

“代码通过测试”只能证明代码行为，不能单独证明学习者掌握。掌握证据来自学习者自己的设计、预测、解释、修改和延迟迁移。

## 2. 范围和边界

### 本轮要做

实现顺序明确为 **Runtime → 可复用框架 → Coding Agent**。先验证执行核心，再提炼公共契约、组合入口和扩展接口，最后构建代码任务应用；框架包含 Runtime，不另写一套循环。每完成一个小单元并验证后，再对照 Pi 对应局部源码如何处理同一个问题，不等整个阶段结束才对照。下文阶段表表达知识依赖，框架能力在相关单元验证后逐步提炼，并在完整 Coding Agent 前形成可复用入口。

- 自己实现 Runtime 的关键控制逻辑：任务状态、循环决策、工具契约与执行、Observation、状态更新、停止/重试/暂停、预算、检查点、Trace 与成功门禁。
- 在其上实现受控的 Coding Agent：读仓库、定位、生成修改、运行测试、核对工作区和补丁版本、审查后交付。
- 按教学需要加入 Context/Memory、知识检索、MCP 能力接入、Graph 路由，以及有明确价值时的角色协作。不是为了覆盖名词而硬加模块。
- 加入企业级设计：最小权限、资源隔离、审批、审计、评估、发布回归和资源控制。先做可验证的纵向切片，不声称未经生产环境验证的项目已经可直接上线。

### 本轮不做

- 不实现浏览器/电脑操作 Agent、语音 Agent；原课程第 13、14 章不计入本轮范围。
- 不克隆整个 Pi，不从头实现模型协议、Git、数据库等通用基础设施。
- 不在学习者理解前一次性生成所有模块，也不把导师写的代码算作学习者的工程掌握。
- 不默认在真实业务仓库执行高风险写入、合并或部署；先用模拟工作区或受控测试仓库。

## 3. 技术路线和参考项目

**技术栈：Node.js + TypeScript。** 原因：现有学习材料中的 `planning-lab` 是 TypeScript，Pi 的 Agent Core 也是 TypeScript，可以直接对照核心类型与执行循环。第 0 篇已把 Node 下限固定为 22.18.0，开发依赖固定为 TypeScript 7.0.2 和 `@types/node` 22.20.5；使用 Node 自带测试器和原生 TypeScript 类型移除，并用 `tsc --noEmit` 单独检查类型。具体配置以 `package.json`、`tsconfig.json` 和锁文件为准。

Pi 是**设计参考**，不是本项目首阶段的运行依赖。每个模块先解释需求、由学习者设计并实现，再针对同一行为看 Pi 的局部源码。不要让学习者先通读 Pi 仓库。优先参考：

- Agent 类型与工具契约：<https://github.com/earendil-works/pi/blob/main/packages/agent/src/types.ts>
- Agent Loop：<https://github.com/earendil-works/pi/blob/main/packages/agent/src/agent-loop.ts>
- 有状态 Agent 封装：<https://github.com/earendil-works/pi/blob/main/packages/agent/src/agent.ts>

本项目约定术语：**Runtime** 是驱动一项任务运行的执行核心；**框架** 是包含 Runtime、工具接口、扩展接口等的可复用开发套件；**Coding Agent** 是用框架完成代码任务的具体应用；**企业平台/治理层** 处理跨任务的身份、策略、发布、审计和容量问题。不同项目可能混用这些名称，教学时以责任边界为准。

## 4. 谁做什么

### 第 0 篇

导师负责在本仓库搭建最小项目脚手架、测试入口和教程目录，并写出可独立阅读的第 0 篇。它只证明工具链可用，不提前实现 Agent Loop。第 0 篇已落在 `docs/tutorials/00-project-setup.md`。

### 从第 1 篇开始

1. 导师先在 Codex 对话里讲清本篇的工程问题、系统位置、因果机制和正反例；教程是课后可复用材料，不替代对话教学。
2. 教程给出精确文件路径、接口、必要的完整示例代码或分段代码、注释、运行命令、预期输出及解释。先让学习者预测或设计，再对照实现；不能只给一大段代码让人照抄。
3. 学习者按教程亲手写核心实现。导师阅读实际代码、解释错误、协助调试和运行测试；若要代写某段核心代码，应先明确这是示范，不计学习者掌握。
4. 一个知识单元完成后，用不同故障或输入做迁移。答不完整时指出正确部分和精确缺口，不连续追问到标准答案。
5. 代码、测试和教程核对一致后，才记录该单元完成。进度只按实际证据更新。

每次最多给学习者**一个需要作答的任务**。不要把“苏格拉底式教学”简化成连续问定义；先讲解和建模，再用高价值问题检验因果关系。

## 5. 教程如何写给别人看

系列教程放在 `docs/tutorials/`。每篇都是能脱离聊天记录阅读的独立章节，建议固定结构：

1. 这篇要解决的真实问题，以及完成后能做什么。
2. 先备知识、用中文解释的新术语、它在累计 Agent 系统图里的位置。
3. 一条可跟踪的正常轨迹和至少一条反例/失败轨迹。
4. 文件清单：每个文件的相对路径、职责，以及本篇究竟新增或修改了什么。
5. 分步实现：代码块、必要注释、关键语句为什么这样写；避免只展示最终文件。
6. 对应测试：测试在防什么错误、怎样运行、预期输出是什么；列出常见报错和排查方向。
7. 本篇不解决什么，下一篇在此基础上加什么。
8. 一道理解/迁移练习，以及可折叠或明确分隔的参考解释，供自学者核对。
9. 对照 Pi 的**一个局部行为**，说明相同设计点和本项目暂未处理的复杂边界。

写作口吻像有经验的人带新人动手：具体、诚实、有取舍。不要堆概念词、空泛口号或机械的“首先/其次/最后”；重要判断说明原因。代码注释帮助初学者看懂**不明显的意图和边界**，不要逐行复述代码，也不要在教程里留下不能运行的伪代码冒充最终实现。

### 教程与代码一致性规则

- 后续教程编写与润色使用用户指定的 [Waza write skill](https://github.com/tw93/Waza/blob/main/skills/write/SKILL.md)。使用时读取中文与技术说明参考，按 skill 运行标点检查。删去套话和重复，保留事实、因果解释、初学者需要的步骤及代码一致性；不为追求简短而降低讲解密度，不机械替换自然表达。

- 章节代码使用 `chapter/NN-topic` 分支区分，第 0 篇为 `chapter/00-project-setup`。每篇通过 GitHub PR 审查，记录完成时的提交 SHA；后续章节使用新分支，不在旧章节分支累加新章实现。
- 本次用户已授权第 0 篇提交、推送与创建 PR；未授权合并。后续章节仍需用户确认后提交或推送。
- 公开教程保留简明验证标准与故障排查，不加入私教式自测问答及折叠参考答案。

- 教程面向公开读者，只包含工程目标、概念、设计理由、实现步骤、源码对照、调试和验收。不得写入私教分工、导师/学习者角色、对话节奏、个人 review 进度、掌握评估、聊天约定或本机个人路径。上述内部信息只保留在交接与学习记录中。
- 后续每篇交付前检查以上内容。实现范围应按章节描述，不以“当前聊天完成了什么”描述；Pi 对照应直接解释技术差异，不讲述私教流程。

- **本仓库实际可运行源码是唯一代码依据。** 教程中的正式实现片段从已完成、已测试的源码核对，不凭记忆重写一份近似代码。
- 每篇要标明对应的章节版本/提交。后续章节会修改同一源文件，因此“第 1 篇代码与第 1 篇完成时的代码一致”，而不是强求它永远等于最终 `main`。是否创建提交、标签或推送，由学习者确认后执行；当前没有任何章节标签。
- 每篇完成前逐个检查：文件路径、导入、命令、依赖版本、代码块、测试和输出是否与该章节实际代码一致。若增加自动核对脚本，应让脚本检查真实代码片段，而不是只检查文档格式。
- 发现教程错误时，修订教程并重新验证；学习者反馈优先于“文档已经写完”的进度标记。

## 6. 建议的课程实现顺序

顺序是学习依赖，不是已经承诺的最终目录或 API。开始每篇前仍要对照实际代码和学习反馈微调。

| 阶段 | 做出的最小结果 | 核心知识 |
|---|---|---|
| 00 环境 | 项目脚手架、测试与类型检查可运行 | 工具链与目录边界 |
| 01 最小闭环 | 假模型驱动一轮可观察的 Agent Loop | Goal、State、Action、Observation、Update |
| 02 工具层 | 类型化工具注册、参数校验、结构化结果 | Tool Calling、失败分类 |
| 03 上下文 | 任务现场与模型上下文分离 | State、Context、Memory |
| 04 控制流 | 有界循环、停止条件、计划和失败路由 | Planning、Graph、Runtime |
| 05 Coding Agent | 受控读写、工作区版本和同补丁验证 | Code Agent 工程闭环 |
| 06 恢复与治理 | 权限、审批、检查点、Trace、预算 | 安全、可恢复性、企业约束 |
| 07 知识与扩展 | 有需要时接 RAG、MCP、角色协作 | 外部知识、能力接入、多 Agent |
| 08 质量闭环 | 场景评估、回归、故障复盘 | Evaluation 与发布门禁 |

不要把所有能力塞进第 1 篇；每个阶段应有能运行的最小结果与可解释的测试。重要复杂性在后续阶段逐步引入。
